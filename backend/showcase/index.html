01 / THE NEED

为什么做 Landing Check

在公开旅行社区里，我们看到一些游客已经查过攻略、装好应用，甚至完成了绑卡，却仍然担心到了中国不能付款。也有人在落地后才发现，自己不知道怎样完成买水这样简单的一笔消费。这些具体的提问让我们开始关注：游客做过准备之后，怎样才能在现场把工具用起来？

点击卡片查看原话与出处

卡片标题为公开原帖的释义。点击查看具体情境、已知后续与原始来源。

攻略已经帮游客做了不少准备

Instagram 上的创作者会介绍来华前需要安装哪些应用、准备哪些东西。这类攻略是有用的起点。我们把它们和游客自己的追问放在一起看，想弄清楚哪些信息已经讲明白了，哪些操作到了实际使用时还会让人犹豫。

因此，我们把目标用户收窄为首次来华、能够自己安排机票和酒店的外国自由行游客。他们通常愿意做准备，需要的是知道自己的设备和账户适用哪种办法，以及出问题后还能怎么办。我们选择从起飞前到离开机场这一段开始，把上网、支付和去酒店的步骤放到同一个行程里。

这个选择也有边界。社区里的求助说明问题确实存在，但不能告诉我们有多少游客会遇到，也不能证明一套连续引导一定比攻略更好。“第一小时”只是我们用来控制产品范围的说法，实际是否能减少摸索，还需要让目标用户完成具体任务来比较。

调研资料与核对方式+

我们对照公开原帖、评论和作者后续回复，保留具体情境和原始链接。游客的求助、个人经历和创作者攻略分别使用；如果问题后来已经解决，来源记录也会保留这个结果。这里展示的是定向收集的案例，没有把帖子热度换算成需求发生率。

02 / THE EXPERIENCE

产品怎么用

Landing Check 被设计为 Trip.com 内的一项功能。我们希望利用用户已有的航班和酒店信息，在起飞前提醒他确认准备情况，落地后再按当前需要给出联网、支付和交通指引。下面的 H5 原型展示了这条流程；点击不同阶段，可以查看具体页面和操作方式。

支付准备按一件事来检查

行前检查里，支付宝和 TenPayGo 放在同一个“境内支付”板块。用户选择一种方式完成小额测试后，这项任务就显示为已完成，另一种可以作为备用；如果测试失败，页面会解释对应错误，并提供切换方式的入口。当前测试使用模拟交易，正式使用前仍需确认支付渠道、退款和结果回调是否能够接入。

支付任务完成后，交通页还会检查具体方案需要什么。例如，支付宝里的滴滴不能通过 TenPayGo 叫车，所以只验证了 TenPayGo 时，页面会提醒用户准备支付宝，或者选择可以付现金的交通方式。我们希望这些条件直接出现在需要做决定的地方。

03 / TECH STACK

技术栈

目前的演示由浏览器里的 H5 和一个 Python API 服务组成。我们用前端展示任务和教程，用后端管理知识条目、识别请求与演示状态。下面是项目实际使用的技术，以及它们各自负责的部分。

前端与原型：HTML、CSS、JavaScript

可交互原型使用原生 HTML、CSS 和 JavaScript。界面设计保存在 appearance.pen 中，经 pen.dev 导出后，由 Python 构建脚本组装页面与点击跳转；app.js 负责调用接口、更新支付和行程状态，以及在后端不可用时切换到静态演示。项目展示页同样使用原生前端，来源弹窗、语言切换和产品流程不依赖后端服务。

接口与规则：Python、FastAPI、Uvicorn

后端通过 FastAPI 提供知识库查询、截图识别、行前检查和交通推荐接口，由 Uvicorn 运行。Pydantic 用来校验请求数据，HTTPX 负责调用模型。行前状态和交通推荐使用明确的规则计算，例如深夜抵达、多件行李或已预订接机时，给出相应方案。目前的航班、订单和支付结果来自模拟接口，运行状态保存在内存中。

场景识别：DeepSeek 与关键词规则

“我卡住了”把用户上传的截图或输入的文字交给 DeepSeek，当前代码默认使用 deepseek-flash。模型需要从已有条目中选择问题类型，并返回条目 ID 和置信度；后端核对 ID 后，再读取对应的操作步骤。不够确定时提供候选让用户确认，模型超时或不可用时尝试关键词匹配。对于知识库没有覆盖的问题，生成建议会明确标为未经核验。

知识内容：JSON 条目与图文教程

知识库直接使用 JSON 文件维护，目前包含支付宝、微信支付、滴滴、上网和 TenPayGo 五类场景，共 41 条记录。每条保存适用条件、操作步骤、备用办法、来源和核验日期；存在争议的数字单独记录，避免直接写进面向游客的指引。Python 校验脚本检查格式和引用，并把带配图的条目导出为 H5 可以读取的教程数据，因此新增内容不必重新编写页面。

测试与部署：pytest、Playwright、GitHub Pages、Render

pytest 检查接口、规则和支付状态，Playwright 在浏览器中走一遍验证成功、失败切换、截图求助和页面返回等流程。10 月 7 日的回归记录为 82 个后端测试和 19 个 H5 端到端测试通过。静态展示页和 H5 发布在 GitHub Pages，FastAPI 服务部署在 Render；模型密钥只配置在服务端。这样的结构让评委可以直接用手机打开原型，同时保留不依赖后端的静态演示。

04 / OUR REFLECTIONS

我们的思考

做这个项目时，我们逐渐把注意力放到几件很具体的事情上：游客怎样判断自己准备好了，遇到报错时应该得到什么帮助，以及前一个步骤的结果如何影响后面的选择。这些问题决定了现在的产品，也留下了还需要验证的地方。

先明确游客眼前要完成什么

来华旅行可以涉及翻译、点餐、景点预约和行程规划，最早的方案也考虑过不少场景。继续看游客的具体求助后，我们更在意的是：一个人已经知道要装哪些应用，到了实际操作时却还是拿不准。于是我们把这次原型收窄到上网、支付和到酒店，并把能提前处理的准备放到起飞前。这样每一页都有一个明确任务，也能说清楚为什么此时需要它。

不过，选定这个范围不代表它已经得到完整验证。有人通过攻略和社区回复就顺利完成了旅行，机场工作人员也能提供帮助。Landing Check 是否值得使用，要看它能不能让游客更快找到适用办法、少做几次错误尝试；仅仅把现有信息集中展示，还不足以说明这一点。

两种支付应用，仍然是一个准备任务

接入 TenPayGo 时，我们最初给它和支付宝各放了一行。界面上虽然多了一个选择，却也让同一件“准备付款”的事看起来变成了两个待办。后来我们把它们合成一个 Payment in China 板块：任一种验证通过，支付任务就算完成，另一种作为可选备用。这个调整提醒我们，页面应该按游客要办的事情组织，接入了几个应用不应该直接决定清单有几项。

同时，一次小额测试能说明的事情也有限。它可以帮助确认某次交易是否完成，却不能保证所有商户、叫车和地铁场景都能使用同一种方式。TenPayGo 在境外能否测试、Trip.com 能否提供对应收款与退款能力，也还需要对接确认。因此，我们既保留支付测试的设计，也把具体交通方案的支付条件和备用办法写出来。

相似的报错，需要不同的处理

TenPayGo 和微信支付可能出现同一句银行拒绝提示，如果只看报错文字，很容易选错应用。我们因此把界面特征、应用名称和关键词一起作为识别线索；看不清时，让用户确认候选，而不是直接给一组看似肯定的步骤。模型负责匹配问题，已经覆盖的问题则从知识库读取答案，方便之后核对和更新。

样本评测也让这个问题更具体。64 张已标注指南截图的场景命中率约为 94%，换成 75 张 Reddit 用户截图后约为 84%。真实截图里有失败弹窗、翻译浮层和缺少上下文的页面，比教程中的标准画面更难判断。这些数字衡量的是场景分类，游客是否照着步骤解决了问题，还需要另做任务测试。TenPayGo 的真实失败截图目前也不足，尚未单独评测。

完整流程也要经得起失败和重试

联调时，我们遇到过重复点击验证、请求迟迟不返回、失败页残留成功文案，以及新截图上传后被旧识别结果覆盖等问题。单看某一张页面，这些地方并不显眼，连着操作才会暴露出来。后续修复加入了重复请求处理、超时重试和过期响应拦截，再用端到端测试检查不同页面是否读取同一份状态。

这也影响了我们对完成度的判断。按钮能点、正常流程能走通，只是演示的起点；游客在机场可能重复操作、切走页面或暂时断网，我们还需要考虑他回来时看到什么、之前做过的事是否保留，以及失败后有没有清楚的去向。现有测试帮我们检查了这些已知分支，接下来仍要在真实设备和目标用户的任务中继续验证。

05 / WHAT'S NEXT

接下来做什么

原型已经能把主要操作串起来，下一步需要确认它是否真的省事，并补齐现场使用的条件。我们会先围绕现有流程验证和完善，再逐项推进平台接入。

用真实任务检验这套设计

让首次来华的游客分别用现有攻略和原型完成联网准备、理解支付报错、选择机场到酒店方案，记录完成情况、耗时、错误判断和求助次数。同时继续收集公开求助和用户自愿提供的案例，核对实际解决过程后再补入知识库。“I’m stuck” 后续也会尝试支持现场照片和语音描述，但会先确认这两种输入是否比截图和文字更方便。

补上离线内容和多语言

目前的静态演示不等于完整离线功能。我们计划在起飞前下载机场联网指引、酒店中文地址和常见问题教程，通过 Service Worker 缓存，让弱网时仍能阅读。多语言内容会先预翻译并复核菜单路径与关键步骤，避免游客每次打开教程都要等待在线翻译。

逐项确认 Trip.com 与支付渠道的接入

正式使用需要获授权的行程只读接口、航班状态更新，以及 App 内通知和客服转接能力。获得这些信息后，才能根据真实到达机场、时刻和酒店生成指引；用户需要人工帮助时，也希望能把当前问题和已尝试的步骤交给客服继续处理，减少重复解释。

真实支付验证还需要合作方提供测试交易、退款和结果回调。我们会先确认境外测试是否可行、一次测试能说明哪些条件，再决定怎样展示“已验证”。如果某种方式只支持落地后交易，行前就检查安装与配置，落地后再确认付款结果。上述能力目前仍是接入计划，演示中的航班、行程和支付继续使用模拟数据。
