## 2. 数据模型

### 2.1 `trip.json`

```json
"payment_apps": {"alipay": {"installed": true}, "tenpaygo": {"installed": false}}
```

### 2.2 `MockTrip` 内存状态

```python
self.payments = {
  'alipay':   {'method': 'alipay',   'status': 'not_verified', 'tx': None, 'verified_at': None},
  'tenpaygo': {'method': 'tenpaygo', 'status': 'not_verified', 'tx': None, 'verified_at': None},
}
```

- `payment`（只读属性，兼容旧调用方）= 第一个验证成功的那条；都没验证时返回支付宝那条。"第一个"按 `verified_at` 排序。
- `get_trip()` 同时返回 `payment`（兼容）和 `payments`（新）。
- 时间线 `payment` 事件加 `method` 字段。两种方式各记一次，不去重；完成页按 primary 取时刻。

### 2.3 方式常量

```python
PAY_METHODS = {'alipay': 'Alipay', 'tenpaygo': 'TenPayGo'}   # mock.py，rules 和 app 引用同一份
```

## 3. 接口

### 3.1 `POST /mock/pay-test?fail=&method=`

| 参数 | 默认 | 说明 |
|---|---|---|
| `method` | `alipay` | `alipay` / `tenpaygo`，其他值返回 400 |
| `fail` | false | 模拟失败 |

成功返回（新增 `method`，其余字段与现在一致）：

```json
{"method": "tenpaygo", "status": "verified", "tx": "TRIP...", "verified_at": "...", "amount": 1.0,
 "currency": "CNY", "refund": "issued", "card": "Visa ••4471"}
```

失败返回：

```json
{"method": "tenpaygo", "status": "failed", "error_code": "ISSUER_DECLINED", "hint": "...", "entry_id": "tenpaygo_card_bind_failed"}
```

| method | error_code | entry_id |
|---|---|---|
| alipay | CARD_NOT_SUPPORTED / RISK_REJECT / LIMIT_EXCEEDED | `alipay_card_bind_failed`（不变） |
| tenpaygo | ISSUER_DECLINED | `tenpaygo_card_bind_failed` |
| tenpaygo | AUTH_FAILED | `tenpaygo_payment_declined` |
| tenpaygo | REGION_UNAVAILABLE | `tenpaygo_setup_before_flight` |

### 3.2 `GET /rules/preflight`

`items` 里 `alipay` 项保留，后面紧跟新增的 `tenpaygo` 项。两项都带 `group: "payment"` 和 `method`。顶层新增：

```json
"payment": {"ready": true, "primary": "tenpaygo", "primary_name": "TenPayGo",
            "verified": ["tenpaygo"], "verified_at": "2026-10-10 08:31:00"}
```

计数规则：

```
required = 非组项中状态为 done/todo 的数量 + 组数（1）
ready    = 非组项 done 数 + 组内任一 done 记 1
optional_open = 非组项 optional 数（组内备用不计）
backup_open   = 组内 optional 数（新字段）
```

### 3.3 `POST /rules/preflight/done`

`item` 白名单加 `tenpaygo`，效果与验证成功相同（演示用，不写时间线）。

## 5. 前端实现要点（`h5/app.js`）

### 5.1 注入时机

TenPayGo 行、选择层、验证页文案切换都放在 `if (!API) return` **之前**，静态模式也可用。接后端的逻辑放在之后。

### 5.2 TenPayGo 行

- 克隆 `Item Alipay payment` 整个节点（含 Row、State、Item Texts、Item Button），改 `data-pencil-name` 为 `Item TenPayGo payment`，去掉克隆来的 `data-pencil-id`，删掉克隆来的教程链接后挂自己的。
- 按钮 `data-act="api:paytpg"`。`ITEM_NODE` 加 `tenpaygo` 映射，`renderPreflight()` 无需特殊处理。

### 5.3 验证结果页

把现在只覆盖成功态的 `PAY_OK` 快照，扩展为页面所有文案节点的快照（设计稿原文即支付宝版本），再按 `(method, outcome)` 覆盖：

```
PAY_COPY = { alipay: {...设计稿原文}, tenpaygo: {...§6 文案} }
applyPayCopy(method)          // 标题区以外的静态文案：已测试第 2 条、失败说明卡、来源小字
renderPayOk(r) / renderPayFail(r)   // 带 method，失败原因表按 method 取
```

失败态在 `Footer` 的 Done Button 下插入 `Use {other} instead ›` 文字链接，成功态隐藏。

### 5.4 选择层

在 `#phone` 内插入一个绝对定位的底部面板（半透明遮罩 + 白色圆角卡片，两行选项 + Not now），样式取设计稿色值。`pay2` 动作改为：组已就绪则直接继续，否则打开选择层，选择后 `S.payReturn = 'step3'` 再调 `pay(method)`。

### 5.5 读支付组

新增 `payState(pf)`：

```js
pf.payment ? { ready: pf.payment.ready, method: pf.payment.primary, name: pf.payment.primary_name }
           : { ready: alipay.status === 'done', method: 'alipay', name: 'Alipay' }   // 旧后端降级
```

替换现有 5 处 `pf.items.find(i => i.id === 'alipay')`：`renderTransport`、`renderDone`、`loadState`、`renderSteps`（经 loadState）、`renderTripsCard`。

### 5.6 动作分发

| 动作 | 接后端 | 静态模式 |
|---|---|---|
| `pay` | `pay('alipay')` | 支付宝成功页 |
| `paytpg` | `pay('tenpaygo')` | TenPayGo 成功页 |
| `pay2` | 选择层 → `pay(method)` | 选择层 → 对应成功页 |

## 6. 识别

- `scenarios_block()` 自动包含新场景，代码不改。
- `classify.txt` 加规则 6：TenPayGo 是独立 App，首页是 Bank Card / Apple Pay / E-Wallet 三张卡片，底部只有 Pay 和 Go 两个标签和扫码键，没有 Chats / Contacts / Discover / Me；看到 TenPayGo 字样或这些特征选 `tenpaygo`，即使报错句与微信相同。
- 规则兜底：`detect.keywords_en` 含 `TenPayGo`、`E-Wallet`、`Supported Payment Methods`、`Show payment code` 等；报错句 `The bank did not approve this transaction` 只放进 `entry_keywords`，不放进场景关键词，避免把微信截图抢过来（FR-8 第二条验收）。

## 8. 兼容与回滚

- 旧 H5（PWA 缓存）连新后端：只认 `alipay` 项，TenPayGo 行不出现；用户若曾用 TenPayGo 验证，旧 H5 会把支付显示为未就绪。演示数据重启即归零，影响可接受。
- 新 H5 连旧后端：`payState` 降级；TenPayGo 行出现但 `Verify ¥1` 走旧接口时 `method` 参数被忽略，结果按支付宝返回。PR 合并后 Render 与 GitHub Pages 同一提交上线，窗口很短。
- 回滚：整个功能在一个分支，revert 合并提交即可；无数据迁移。

## 9. 评审后的变更（2026-10-06）

代码评审提出 10 条意见，全部采纳。与上文不同的地方：

| 变更 | 位置 |
|---|---|
| `PAY_METHODS` 从 `mock.py` 移到 `rules.py`（规则引擎不依赖模拟数据层），`mock.py` 和 `app.py` 从 `rules` 引入 | §2.3 |
| `primary` 排序：有 `verified_at` 的（真做过 ¥1 测试）优先于只被 `/rules/preflight/done` 标记的 | §3.2 |
| `rules.transport(..., paid=)`：新增参数，传入已验证方式；`transport.json` 的 `needs_alipay` 在没有支付宝时变成输出里的 `pay_note`。新增 `rules.verified_methods()` 供 `app.py` 调用 | 新增，对应 PRD FR-12 |
| 场景关键词去掉 `财付通`、`深圳通`、`Tenpay`（财付通是微信支付的运营方，会出现在微信账单里） | §6 |
| 提示词规则 6：只有共用报错句、看不出是哪个 App 时优先 wechat、置信度约 0.5、TenPayGo 作为第二候选，与规则兜底一致 | §6 |
| 失败页：另一种方式已验证时，链接改为 `{方式} is already verified · you can pay ›` 回行前检查，不再发起第二次 ¥1；客户端不认识的错误码用通用说明；网络失败显示本次方式的 `NO_CONNECTION` 失败页 | §5.3 |
| 教程入口的截图张数从 `tutorials.json` 读取；`tutorials.json` 只请求一次（`loadTutorials()`） | §5.2 |
| `validate_entries.py` 的外链白名单改为按域名判断；应用商店只放行 TenPayGo 的两个官方页面 | §1 |

## 10. 风险

| 风险 | 对策 |
|---|---|
| 克隆的 DOM 节点带有设计稿的 `data-pencil-id`，与 `build_h5.py` 的 BIND 冲突 | 克隆后删除所有 `data-pencil-id`，按钮改用 `data-act` |
| 验证页文案快照时机：若在后端渲染之后才快照会存进错误文案 | 在注入代码最前面快照，早于任何 `renderPay*` |
| 识别把 TenPayGo 认成微信 | §6 规则；没有样本，测试报告写明未评测 |
